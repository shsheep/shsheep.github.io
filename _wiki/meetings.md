# 202401021500 한화생명 회의

- 한화생명 데이터 : 송민호 대리
- 한화생명 아키텍처 2인
- 한화생명 클레임(코어) 2인

- *이돈호 이사님, 민찬님, 창현님은 회의실 사정으로 불참

## 안건
- OCR 요청을 한 번의 콜로 해결하면 안되는 것인지, 반드시 두 번의 콜을 수행해야 하는 것인지.

## 입장
1. 업스테이지
    - 기술적으로 불가능하다기 보다는 향후 유지보수 관점에서 두 번의 콜이 낫기 때문에 이렇게 제안드리고 싶다.
    - 두 번의 콜로 나누는 것이 유지보수 관점에서 좋으며 현재 솔루션이 그렇게 설계되어 있다. 두 번의 콜을 하나로 합치게 되면 내부적으로 한화생명 문서분류 코드를 처리하는 로직이 들어가 일반적인 기능을 탑재하기가 어려워진다.
2. 한화 아키텍처, 한화 클레임
    - 한 번의 콜로 될 수 있으면 좋겠다.

## 논의된 내용
1. 단일 요청
    - (업스테이지) 단일 요청이 기술적으로 불가능하다기 보다 향후 유지보수 관점에서 두 번의 요청이 낫기 때문에 이렇게 제안드리는 것. 문서분류기는 한화생명 특화 모델로 인풋에는 데이터 매트릭스가, 아웃풋에는 한화생명 문서 코드가 포함되어있다. 단일 요청으로 문서분류 + 추출을 합쳐버리게 되면 내부적으로 한화생명 문서분류 코드를 처리하는 로직이 들어가 일반적인 기능을 탑재하기 어려워진다.
    - (한화 아키텍처) 업스테이지는 순수하게 OCR 엔진만 제공해주는 것이고 특정 서식에 대해 OCR을 태운 결과값만 관리하기 때문에 이미지를 받아서 OCR을 태우는 역할은 게이트웨이에서 해주는 것이다. 클레임뿐만 아니라 타 조직까지 쓸 것까지 염두에 두어야 해서 게이트웨이가 필요하고 게이트웨이에 단일 요청과 같은 클레임 측의 비즈니스를 녹여서는 안될 것 같다. 게이트웨이가 단일 요청만을 클레임으로부터 받아서 문서분류 + 추출까지 해주는 방식도 비즈니스 판단이 들어가야하기에 비즈니스(클레임)의 관여가 들어가는게 좋을 것 같다.
2. 테스트
    - (한화 클레임)ASIS에는 클레임 측이 무언가를 호출하는 로직이 없었고 클레임 측이 새로 무언가를 호출을 하도록 변경. 다만, 클레임 측 공수가 늘어나 업스테이지 OCR과의 테스트를 전부 수행해보지 못 할 수 있다.
    - (한화 아키텍처) 한 사이클만이라도 해볼 수 있을 것 같다.
    - (한화 아키텍처) 현행 데이터 중 최대 멀티 페이지 장 수가 6~700장 정도였고 평균적으로는 수 십여장 정도였다, 단 데이터 내의 모든 페이지가 5종 문서는 아니었다. 통합테스트가 2월 초인데 업스테이지 측에서 성능 테스트 시나리오를 탄탄하게 준비해주기를 바란다.
