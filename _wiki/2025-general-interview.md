        - 이전 직장에서 C언어 기반으로 국내 주식시장의 매매체결 시스템을 개발하고 운영하는 일을 하며 커리어를 시작했고, 현 직장으로 올 때는 제가 만드는 서비스가 세상에 좀 더 큰 임팩트를 주었으면 하는 바람으로 옮겨 왔는데, 이곳에서 이를 더 여실히 느껴서 오늘 이렇게 네이버 통합검색 백엔드 부문에 지원하게 되었습니다. 이번 시간 잘 부탁드립니다.
        - 이전 직장에서 주식시장 매매체결 시스템을 관리하면서 사내 개발자들이 공통으로 사용하는 기술과 프레임워크를 개발하는 일을 하며 커리어를 시작하였고, 현재는 AI 스타트업에서 AI 제품을 A부터 Z까지 주도적으로 책임지며 만들고 있습니다. 이번 시간 잘 부탁드립니다.
    - (왜 현 직장은 임팩트가 부족하다고 생각하느냐) 우선 세상에 대한 임팩트는 상대적인 것이라고 생각합니다. 저는 좀 더 큰 임팩트를 느끼고 싶어서 검색/하이퍼로컬 도메인에 관심을 가지게 된 것인데요, 현 직장의 AI OCR, 그리고 LLM 도메인도 충분히 뚜렷한 임팩트를 내고 있습니다. 다만 제가 일을 하면서 기여했고, 앞으로도 기여하게 될 도메인이 보험사 같은 금융권에 특화되어 있다고 생각이 되어 제가 지향하는 넓은 범주의 '개방된' 도메인들과는 다소 차이가 있다고 느꼈습니다. 쉽게 말해 살면서 이러한 금융 도메인을 접하게 되는 순간은 많지 않고 때문에 저는 좀 더 삶의 많은 부분을 차지하는 도메인에서 엔지니어링을 수행하고 싶었습니다.
2. 왜 이직하려고 하나요?
    - 요약해서 말하면 첫 직장에서 개발을 재밌게 했던 기억을 토대로 새로운 도전을 하고 싶어서 이직을 생각하게 되었습니다.
        - 현 회사는 이제 시리즈 C 넘어가는 스타트업인데 저는 시리즈 A 단계에 합류하였다. 당시 업무나 엔지니어링 프로세스가 정립된 것이 하나도 없어서 정말 열심히 일하며 프로세스를 수립했다. 필요한 것들 하나하나 다 구현하고 준비했다.
        - 그렇게 기반을 만들고 나니 현재는 솔루션과 서비스가 안정화 되었는데 점점 몸이 편해지고 고여가는 느낌이 들었다.
        - 안락한 현실에 안주하고 싶지 않고 새롭게 도전하고 싶은 생각이 들었는데 첫 직장에서 C를 재밌게 했던 기억과 현 직장으로 올 때 제가 만드는 서비스로 세상에 임팩트를 주고 싶다는 생각이 다시금 떠올랐다. 이러한 취지에 모두 부합하는 네이버 통합검색 백엔드 부문을 알게되어 지원하게 되었다.
    - 개발자로서 주도적으로 성장하고 싶어서 이직을 결심하게 되었습니다. 저는 개발이 하고 싶고 개발자, 즉 개발을 잘하는 직장인로서 성장하고 싶은데, 회사에서 점점 고객사에 출장을 나가서 유지보수를 하는 필드 엔지니어 롤을 맡겨서 주도적으로 일을 하며 제가 원하는 성장을 하고 싶어서 이직을 결심하게 되었습니다.
        - 회사의 금융권 엔터프라이즈 고객이 많아지면서 필드 엔지니어가 필요해졌는데 이 롤을 금융권 경험이 있다는 이유로 저에게 원하고 있습니다.
        - 백엔드 개발자로서 성장하고 싶어서 현재 롤보다 더 주도적으로 서비스를 개발하고 운영하는 일을 하고 싶어서 지원했습니다.
        - 고객사에 출장을 나가는 방식의 엔지니어링도 필요한 일이었기에 그동안 재미를 붙이려고 노력했고 열심히 수행했다. 다만 고객사 내부 시스템 integration 과정에서 고객사와 제가 가지는 합의중 하나가 바로 안전 운영인데요, 저는 안전 운영 측면에서 다양한 장치를 해놓고 싶은데 고객사의 결정으로 이런 장치를 두지 못하는 일이 간혹 있었습니다.  때문에 이제는 제가 하고 싶은 일을 해보고 싶어서 이직을 결심하게 되었다.
3. 본인이 여태 했던 일 중 가장 임팩트가 컸던 일을 하나 소개해주세요.
    - 네 음 규모가 컸던 일과 메트릭이 좋게 뽑혔던 일 두 가지가 있는데요, 규모가 컸던 일은 전직장에서 차세대 프로젝트를 하면서 전사 서비스 이중화를 위해서 TCP 세션을 기반으로 FT 이중화 기능을 구현해서 전사 시스템에 적용한 일이 있고, 메트릭이 좋았던 일은 현 직장에서 OCR API 추론에 병렬처리를 적용해서 레이턴시를 크게 감소킨 일이 있습니다.
    - 규모가 컸던 일
        - 코스콤 서비스 이중화를 위한 TCP FT 기능 개발
            - 전 회사는 국내 주식 시장 매매 체결 시스템을 개발하고 운영하는 서비스를 하고 있었다.
            - 기존에는 상용 미들웨어를 사용하여 서비스 삼중화를 제공하였다. 운영 비용 절감을 위해 상용 솔루션을 걷어내고 삼중화 구조를 이중화로 바꾸는 요구사항이 생겼다.
            - 그래서 active 서버와 standby 서버에 FT 용도의 idle한 TCP 세션을 맺도록하여 active 노드의 장애로 연결이 끊어지면 standby 서버가 activation되도록 구현하였다.
            - 처음에는 이렇게 쉽게 생각하여 TCP가 stateful한 신뢰성 있는 프로토콜이니 한쪽 프로세스가 다운되어 세션이 끊어지는 상황을 모두 금방 감지해낼 것이라고 생각하였다.
            - 그런데 실제 장애 상황을 재현하기 위해서 서버 전원을 차단하거나 랜선을 뽑는 식의 비정상 상황을 만들어내니 standby 서버가 연결이 끊어진 것을 곧바로 감지해내지 못했다.
            - 15분 정도의 시간이 지나서야 세션이 끊어진 것을 감지해냈는데 이 시간은 os의 tcp keepalive 패킷을 보내는 파라미터에 의해 결정되었다.
        - 프로세스 오케스트레이션 데몬 개발
            - 당시 시스템이 베어메탈 위의 non-container로 돌아가고 있었는데 프로세스의 상태를 관리해줄 주체가 필요했었다.
            - parent-child 구조로 fork하여 프로세스의 상태를 관리하고 자동 재기동 해주는 데몬을 개발한 것이 기억에 남는다.
            - 서비스 내용을 컨픽에 작성하면 데몬 서버가 기동하며 컨픽 내용대로 fork 하여 child 프로세스를 만들어내고 그 pid와 시그널 통신을 하며 상태를 점검하는 방식이었고, kill 시스템콜을 사용하여 0번 시그널을 전송하는 것으로 프로세스의 기동 여부를 확인할 수 있었습니다.
            - 또 위에서 말한 FT active-standby 구조의 서비스에 대해서도 dual active를 방지하는데에도 데몬이 큰 역할을 했는데, 컨픽에 이중화 구조로 정의된 두 프로세스가 서로 active로 기동하게 되면 먼저 기동해있는 active를 데몬이 kill하여 dual active를 방지하였습니다. 이는 프로세스가 activation 될 때 유저 시그널 1번을 부모 프로세스인 데몬에 보내는 방식으로구현하였습니다.
            - 프로세스간 시그널 통신을 처리하면서 데이터를 주고 받지는 않았습니다. kill 시스템콜을 사용했는데 만약 데이터를 주고 받아야 했다면 sigqueue 시스템콜로 시그널과 데이터를 전달했어햐 합니다.
    - 메트릭이 좋았던 일
        - 서빙팩에 병렬 추론 적용
            - 문서의 글자를 인식하는 OCR 서비스를 제공하던 중 jpg 같은 싱글 페이지 문서 외에 pdf 같은 멀티페이지 문서도 받아서 처리하였니다. 기존에는 이 pdf 문서의 최대 페이지 수를 100장으로 제한해 두었는데 이를 보험사 카탈로그 같은 문서처럼 3000장까지 확대하도록 하는 기능이 필요하게 되었다.
            - 기존 방식은 10장 짜리 문서가 하나의 요청에 들어온다고 하면 그 10장을 각 페이지로 나누어 for문을 돌며 한번에 하나씩 OCR 추론을 보내어 한 페이지당 2초가 걸린다고 하면 20초가 걸렸다.
            - 서버의 타임아웃이 5분이었는데 100장이면 5분 안에 정상적으로 끝날 수 있었다. 3000장은 그 안에 끝나는게 불가능하여 성능 개선이 필요하였다. 쓰루풋을 위해서 OCR 모델을 여러개 띄워놓는데 10장 짜리 문서가 하나의 요청에 들어온다면 하나의 요청 컨텍스트 내에서 고루틴을 10개 생성하여 각각의 페이지가 동시에 실행될 수 있도록 하였다.
            - 동시성 처리는 크게 어려운 부분이 없었는데 각 고루틴이 각 페이지의 추론 결과를 하나의 배열의 서로 다른 인덱스에 저장하기 때문에 어렵지 않았다. 어려운 부분은 에러 처리 부분이었다.
            - 생성할 고루틴의 개수는 모델 컨테이너의 개수로 정해놓았다. 모델 컨테이너가 10개 떠있어 10개의 고루틴이 생성될 때 20장 짜리 문서가 들어오면 하나의 고루틴이 두번씩 페이지를 처리하게 된다. 20장 중에 한장이라도 페이지가 깨져있거나 하는 이유로 OCR 추론이 실패하면 실패를 응답하는 것으로 정책을 정하였다. 때문에 추론 도중 특정 페이지에서 실패가 발생하면 이후 페이지는 추론을 돌릴 필요가 없었다.
            - 이 과정에서 고루틴간의 에러 전파를 위해서 별도의 에러 채널을 생성하였고 각 고루틴은 OCR 처리 전 에러 채널을 확인하여 에러가 발생하지 않았을 때에만 OCR 처리를 시작하도록 구성하였다.

5. 이전 직장에서 했던 업무와 업무에서 이룬 성과를 설명해주세요.
6. 시스템 콜이란 뭔가요? CPU bound, I/O bound가 뭔가요?
    - 시스템콜은 애플리케이션이 커널이 제공하는 기능을 사용하기 위한 인터페이스입니다.  호출 시 유저 모드에서 커널 모드로 전환하여 OS가 제공하는 기능을 사용하게 됩니다.
    - CPU 바운드와 I/O 바운드는 프로그램의 실행 속도에서 어떤 것이 병목이 되는지를 나누는 개념입니다. CPU 바운드 작업의 경우 복잡한 수학 연산이나 행렬 연산 같이 CPU의 성능이 중요한 작업을 의미하고, I/O 바운드 작업은 파일 I/O나 네트워크 I/O 같이 I/O 작업을 기다리는 과정이 있어 I/O 작업의 성능이 중요한 경우를 의미합니다.
7. 파이썬 GIL이 뭔가요? 파이썬에서 멀티쓰레딩이 가능한가요?
    - Global Interpreter Lock은 하나의 프로세스 내에서 한번에 하나의 쓰레드만 파이썬 바이트코드를 실행할 수 있도록 제한하는 전역 락.
    - 파이썬은 C나 Go와 다르게 인터프리터형 언어이기 때문에 실행 시점에 인터프리터가 코드를 한줄 한줄 바이트코드로 변환하고 이를 실행합니다.

4. keep-alive 란?
    - TCP Keep alive : OS 레벨에서 실제 연결의 유효성을 주기적으로 확인하고 응답이 없으면 연결을 닫아 OS 리소스를 정리해주는 기술
        - 연결이 정상적으로 살아있는지 확인하는 관점.
    - HTTP Keep alive : HTTP 레벨에서 일정 시간동안 연결을 재활용해서 불필요한 TCP 3 way handshake 연결 오버헤드를 줄여 성능을 향상시키는 기술.
        - 연결을 재사용 할 수 있는지 확인하는 관점.
        - 하나의 TCP 연결이 여러 HTTP 요청과 응답에 재사용 될 수 있게 한다.
        - 연결을 맺은 후 필요한 여러개의 요청과 응답을 하나의 TCP 연결 안에서 주고 받는다. 일정시간 동안 추가 요청이 없으면 그 때 연결을 해제한다.
5. stateful과 신뢰성 있다는게 무슨 뜻이에요?
    - stateful : 단순히 데이터를 한번 주고 받고 끝이 아니라 연결을 개시, 유지, 종료하는 것을 의미합니다. 3 way handshake와 4 way termination으로 설명됩니다.
        - 3 way : SYN, SYN+ACK,ACK. SYN_SENT, SYN_RCVD, ESTABLISHED
        - 4 way : FIN, ACK FIN, ACK. FIN_WAIT_1, FIN_WAIT_2, TIME_WAIT, CLOSE_WAIT, LAST_ACK.
    - 신뢰성 : 신뢰성이 있는 이유는 여러 이유가 있는데 에러를 체크섬을 통해 데이터가 손상되었는지를 확인하고 데이터를 순서대로 중복 없이 전달한다는 의미입니다.
        - 순서대로 보낼 수 있는 이유는 TCP가 데이터를 보낼 때 세그먼트의 sequence number에 순서에 대한 정보를 담아서 보내기 떄문입니다. 시스템의 MTU보다 훨씬 큰 데이터를 보낼 때 Maximum Segment Size 이하로 나눠서 여러번 보내게 되는데 받는 측에서는 이 sequence number를 참조하여 데이터를 순서대로 재조립하게 됩니다.
        - 중복 없이 전달될 수 있는 이유는 송신측이 수신측으로부터 ACK를 기다리며 재전송을 결정하기 때문입니다. 
        - 이러한 특성들 때문에 신뢰성 있는 프로토콜이라고 설명이 되는 것 같습니다.

### C
1. malloc/mmap 동작 방식, 물리 메모리 관점에서
    - 두 함수 모두 호출 시점에는 물리 메모리 없이 가상 주소만 확보됩니다. 실제 물리 메모리가 할당되는 시점은 가상 주소의 접근 시점에 페이지 폴트가 발생되어 그 때서야 커널이 물리 페이지를 할당하게 됩니다, 즉 물리 메모리 관점에서 lazy allocation이라고 볼 수 있다.
    - malloc의 경우 일정 크기를 넘어가는 크기의 메모리에 대해서는 mmap을 호출하고 그 미만의 메모리는 sbrk를 호출한다고 알고 있습니다. 그래서 malloc은 작은 크기의 메모리 할당에 최적화되었습니다.
    - mmap의 경우 보통 4kB의 페이지 단위로 할당하는데에 최적화되어 있어 대용량 연속 메모리 할당에 유리합니다. mmap의 경우 MAP_POPULATE 플래그를 사용해서 prefault(pre page fault)를 발생시켜서 물리 메모리를 미리 할당받을 수 있음.

    3. false sharing을 방지하기 위해 cache line 단위로 메모리 할당 및 사용(cache line align)
        - 캐시 라인은 보통 64바이트 등 일정한 크기를 가지며 메모리의 연속된 주소 영역을 한 덩어리로 묶음
        - CPU 코어는 메모리에서 데이터를 가져올 때 이 캐시 라인 단위로 가져온다
        - 멀티쓰레드 환경에서 각 쓰레드가 서로 다른 변수에 접근한다고 해도 그 변수들이 같은 캐시라인에 위치한다면 각 쓰레드는 같은 캐시 라인을 공유하게 됨
        - 멀티코어 아키텍처는 각 코어가 독립적인 캐시를 가지고 있음, 메모리 일관성을 유지하기 위해 cache coherent protocol을 사용함
        - 서로 다른 쓰레드가 동시에 자신이 사용하는 서로 다른 변수에 접근하고 업데이트 하는 경우, 그 변수들이 같은 캐시 라인에 있다면 한 쓰레드가 자기만의 데이터를 변경할 때마다 해당 캐시 라인이 다른 쓰레드의 캐시에서도 무효화됨
        - 이렇게 불필요하게 캐시 라인이 빈번하게 무효화되고 재로딩되는 현상이 발생하면 성능이 저하된다
        - 실제 데이터는 서로 다른 변수임에도 불구하고 같은 캐시 라인 상에 있기 때문이 동기화 문제와 성능 저하를 일으킨다는 의미에서 false sharing이라고 불림
        - C에서는 __attribute__((aligned(128)))  같은 키워드로 cache line padding을 활용함, Go에서는 수동으로 구조체의 멤버 변수 사이에 padding을 붙여줌
        - ```
            const cacheLineSize = 64

            type PaddedCounter struct {
                value int64
                _     [cacheLineSize - 8]byte // 8바이트 int64를 제외한 56바이트 패딩
            }
          ```

5. C/Go의 컴파일 과정에 대해서 설명해보세요. 컴파읽과 빌드란?
    - C의 컴파일 과정은 크게 전처리(preprocess), 컴파일, 어셈블, 링킹의 4 단계로 이루어진다고 설명할 수 있습니다. 
        - 먼저 전처리는 소스 코드내에 정의된 매크로를 치환하고 include 시킨 헤더 파일의 내용을 파일에 포함시키고 조건부 컴파일 로직을 처리합니다. 이렇게 전처리 되고 나면 전처리된 하나의 거대한 소스 파일이 생기게 됩니다.(gcc -E)
        - 그리고 컴파일 단계에서는 이 거대한 소스 코드를 어셈블리어로 변환하게 되는데 즉 저수준 어셈블리어로 코드가 변환됩니다(gcc -S)
        - 이렇게 변환된 어셈블리어 코드를 기계어로 변환하게 되고 이 과정에서 오브젝트 파일이 나오게 됩니다(gcc -c)
        - 마지막으로 오브젝트 파일들을 archive(정적) 혹은 shared(동적) 라이브러리와 묶어서(링크 시켜서) CPU가 실행 가능한 ELF 실행 파일을 생성하게 됩니다.(a.out은 aseembler output이라는 뜻)
6. 동적 링크와 정적 링크 차이가 뭐에요?
    - 정적 링크는 컴파일 타임에 실제 full 링크가 일어나서 아웃풋 파일에 라이브러리의 내용을 포함시키는 빌드 방법이고, 동적 링크는 컴파일 시에는 심볼만 링크하고 런타임에 완전 링크하는 방법입니다. 정적 링크는 라이브러리의 내용이 실행 파일에 포함되기 때문에 실행 파일의 크기가 다소 크고 동적 링크는 shared library가 실행 파일과 따로 있어 실행 파일 크기가 다소 작습니다. 때문에 정적 링크는 실행 시점에 해당 archive 라이브러리가 없어도 온전히 실행이 가능하지만 동적 링크는 실행 시점에 .so 파일이 LD_LIBRARY_PATH 상에 존재해야 실행이 가능합니다.

8. C/Go 좋아해요?
    - 네 제가 C/Go 좋아하는 이유는 크게 두가지인데요, 먼저 언어가 간결하다고 생각이 되어서 좋아합니다. 파이썬이나 혹은 자바스크립트 같은 언어를 보면 언어 차원에서 예외 처리 기능이 제공되는데 그런 기능은 분명 좋은 기능이지만 소스코드를 읽는 측면에서는 복잡성을 증가시키는 것이 자명하다고 생각됩니다. C 같은 경우는 저는 과장 조금 보태서 위에서 아래로 쭉 읽으면 된다고 표현하는데, 언어가 단순하기 때문에 프로그래머의 생각을 소스 코드로 표현하는데에 유리하다고 생각됩니다. 규모가 큰 리눅스 커널 소스 같은 것을 보면 매크로가 방대하게 선언되고 쓰이고 있어서 복잡해지는 경우가 있기는한데, 저 같은 경우는 그럴 때 매크로 호출부를 매크로 내용으로 치환시켜서 읽음으로서 해결하고는 합니다.
    - 둘째로는 C와 Go가 강력해서 좋아합니다. 특히 C는 OS 레벨에서 하드웨어와 밀접한 위치에서 애플리케이션의 성능을 튜닝할 수 있어서 성능을 극한으로 끌어올릴 수 있다는 것이 장점이라고 생각됩니다. 가령 false sharing을 방지하기 위해서 메모리 패딩을 사용한다던가 혹은 C에서 제공하는 메모리 얼라인 키워드를 사용한다던가.  아니면 파일에 데이터를 write할 때 fwrite를 쓰면 쓸 데이터의 내용이 그 즉시 파일에 쓰여지지 않고 라이브러리 버퍼나 커널 퍼버 단계에 머무르고는 하는데 이럴 때 명시적으로 flush를 해주어서 파일 write를 즉시 수행할 수 있도록 하는 등 이런 언어의 메커니즘이 컴퓨터와 일맥상통하는 점이 매력적이라고 생각됩니다.

### Linux
1. ELF란?
    - Executable and Linkable Format. 유닉스 계열 운영체제에서 사용되는 실행 파일 등의 바이너리 파일 형식
2. stack memory vs heap memory
    - 스택 메모리: 메모리 상에서 스택 영역이 차지하는 공간. 함수 호출 시 할당되며 종료되면 해제된다. 일반적으로 크기가 몇 MB 정도로 작음.
    - 스택 메모리가 한계에 도달하면 스택 오버플로우 발생
    - 힙 메모리 : 메모리 상에서 힙 영역이 차지하는 공간. 프로그래머가 직접 할당하고 해제한다. OS의 가용 메모리에 따라 상대적으로 크기가 큼.
3. process vs thread
    - 프로세스는 OS로부터 자원을 할당 받은 작업의 단위
    - 쓰레드는 프로세스가 할당 받은 자원을 이용하는 실행 흐름의 단위
    - 프로세스 컨텍스트 스위칭이 쓰레드 컨텍스트 스위칭보다 비용이 많이 든다.
        - 프로세스가 바뀌면서 캐시 미스가 발생될 가능성이 높음.
        - 프로세스마다 서로 다른 주소 공간을 사용하기 떄문에 메모리 맵을 변경해줘야 함
        - 전환 대상은 각각 PCB와 TCB인데 PCB가 더 크다. PCB에만 있는 것은 FD 테이블, PID, UID, GID 정보, 프로세스 메모리 맵 등이 있음
4. 스왑 메모리란?
    - 스왑 메모리는 메인 메모리가 부족할 때 스토리지를 메모리처럼 사용할 수 있도록 하여 메인 메모리가 부족해도 프로세스가 유지될 수 있도록 하는 기술

### Web
1. GET vs POST
    - GET은 서버에 데이터를 요청할 때, POST는 서버에 데이터를 전송할 때 사용합니다. 때문에 GET은 멱등성이 보장되나 POST는 멱등성이 보장되지 않습니다.
    - GET은 브라우저나 프록시 서버에서 캐싱 될 수 있는데, POST는 기본적으로 캐싱 되지 않습니다.
    - 데이터 전달 방식도 GET은 URL에 쿼리 스트링으로 요청하기 때문에 민감한 정보 전송에는 부적합합니다. POST는 요청 body에 데이터를 포함시키기 때문에 상대적으로 보안에 좋습니다.

    - 저희는 helm이나 kustomize 같은 도구를 사용하지 않고 kubectl과 쌩 yaml 파일로 쿠버네티스 서비스를 배포했는데요. 솔루션의 초기 버전에는 rate limit 기능이 포함되어 있지 않아서 들어오는 요청들을 모두 받아들여서 이미지 변환을 시도하는데 이 과정에서 메모리를 많이 쓰게 되었고 이를 garbage collection 할 때 CPU limit에 걸려서 쓰로틀링이 발생하였습니다. 프로메테우스로 CPU 쓰로틀 메트릭을 볼 수 있다고 알고 있는데 당시 프로메테우스로 모니터링을 하지 않고 상용 솔루션(제니퍼 소프트)을 사용하고 있어서 솔루션 숙련도가 높지 않아서 이 부분을 모니터링하는 방법을 미리 대비해놓지 못 하였습니다. 그래서 직접 pod의 cgroup 레벨에서 쓰로틀된 횟수와 시간을 확인할 수 있는데 실제로 확인해보니 상당한 횟수와 시간이 쓰로틀된 것을 확인했습니다. 해당 서비스를 guaranteed QoS로 유지하면서 cpu limit을 해제하니 더 이상 성능이 튀는 일과 쓰로틀링 발생이 없어졌습니다. 추후 찾아보니 쿠버네티스 가이드 문서에 CPU 리밋은 신중하게 걸어야 한다고 나와 있었습니다. 
    - 또 다른 장애 상황으로 다소 초보적인 장애 상황이 있었는데요, 쿠버네티스 인증서가 만료되는 시점을 관리하지 못한 일도 있습니다...
