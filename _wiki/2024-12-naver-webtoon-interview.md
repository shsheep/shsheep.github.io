    - 전체 OCR 추론 파이프라인이 처음에 이 문서분류기 모델에 먼저 추론 요청을 보내서 어떤 문서인지 판별해내고, 그 결과에 따라 다른 모델을 선택하는 식으로 해서 추론 파이프라인이 결정되기 때문에 이 모델이 가장 앞단에서 빠르게 요청을 처리해줘야 했습니다, 즉 bottleneck이 되어서는 안됐습니다.
    - throughtput을 위해 문서분류기 모델을 여러대 띄워놓는데 로드 밸런싱이 잘 되지 못해(모델에 추론이 잘 분배되지 못하여)  모델이 idle한 상태로 있는 등 GPU 사용률이 100%가 되지 못하면 전체 추론 파이프라인 시간도 늘어나고 비싼 GPU 하드웨어도 낭비되게 됩니다. 때문에 API 서버에서 OCR 요청을 각 문서분류기로 빠르게 분배해주어야 했습니다. 같이 일하던 시니어 개발자분께서 redis가 굉장히 튼튼한데 redis 자료구조를 이용해서 로드밸런싱을 해보자고 아키텍처를 디자인해오셨고 이 설계를 기반으로 redis의 list 자료구조를 기반으로 라운드 로빈 방식의 로드 밸런싱 로직을 구현하였습니다.

        - 여러 프로세스를 컨픽상에 트리 관계에 있도록 묶어놓아 기술한 뒤 단일 최상위 부모 프로세스에서 해당 프로세스들을 fork시켜 기동하도록 하였고 동시에 해당 프로세스들의 pid를 최상위 부모 프로세스가 모니터링하고 관리하도록 하였습니다. 어느 한 프로세스가 비정상 종료되었을 때 그 exit code가 서킷 브레이크 코드라면 부모 데몬 프로세스가 해당 프로세스 하위의 프로세스들을 순차적으로 종료시키도록 하였고 이 과정에서 kill 시스템콜로 시그널을 보내 프로세스를 종료시켰습니다.
    - 이 과정에서 데이터 부정합 이슈가 세그멘테이션 폴트와 함께 발생하는데 C에서는 예외 처리 기능이 없어서 세그멘테이션 오류가 발생할 때 어느 함수에서 오류가 발생했는지 추적이 잘 되지 않았습니다. 이 때문에 세그멘테이션 폴트 발생 시 함수 호출 스택을 출력하는 스택 트레이스 기능을 자체적으로 구현하여 트러블 슈팅에 대한 비용을 대폭 줄였습니다.
        - 잘못된 메모리 주소에 접근하여 세그멘테이션 폴트가 발생할 때 발생한 쓰레드에서 SIGSEGV 시그널이 발생하게 되는데 이에 대한 시그널 핸들링 루틴을 구현하는 것은 어렵지 않았습니다. 다만 해당 쓰레드가 멀티 쓰레드로 구성되어 있는 프로세스에 속한 하나의 쓰레드였고,  때문에 해당 쓰레드에 SIGSEGV 시그널에 대한 기본 작동방식,  스택 트레이스를 출력하지 않고 즉시 종료, 을 block했어야 했는데 해당 쓰레드가 메인 쓰레드였습니다.
        - 메인 쓰레드에 특정 시그널에 대한 blocking을 적용해놓으면 이후 생성되는 다른 쓰레드도 메인 쓰레드와 동일하게 그 시그널이 block 되게 됩니다. 때문에 다른 쓰레드 생성이 완전히 종료되고 난 다음 시그널 block 설정이 진행되어야 했습니다.

1. Go의 select와 C의 I/O multiplexing select 차이가 뭔가요?
    - I/O multiplexing이란 단일 컨텍스트에서 여러 I/O 데이터를 동시에 처리하는 기술을 의미합니다, 여기서 컨텍스트는 주로 프로세스나 쓰레드를 의미합니다.
    - 예를 들어서 Go에서는 하나의 고루틴에서 여러 채널로부터 들어오는 데이터를 참조해서 각각에 따른 로직을 전개할 수 있는데 이 때 각 채널로 들어오는 데이터들을 동시에 처리할 수 있는 기능이 I/O multiplexing입니다.
    - 또 C에서는 libevent의 epoll이나 select를 사용해서 하나의 서버가 여러개의 클라이언트와 동시에 통신할 수 있는데, 이 때 통신해야할 네트워크 소켓들을 fd set에 추가한 뒤 해당 fd set에서 발생하는 이벤트를 감지하게 됩니다
    - 공통점
        - 둘 다 여러 작업이나 이벤트를 동시에 기다리면서 준비된 작업을 처리
        - 둘 다 작업을 비동기적으로 처리하여 동시성을 지원
    - 차이점
        - `Go select는 프로세스 내의 채널 통신을 다룰 때 사용되며 채널로 들어오는 데이터를 비동기로 감시하는 역할을 합니다.`
        - `C의 select는 소켓이나 파일 같은 FD의 읽기, 쓰기, 예외 상태를 감시하는 네트워크나 I/O 작업에 사용`
        - Go select는 라이브러리 의존 없이 사용할 수 있는 Go의 기능. C는 select는 libevent 라이브러리의 기능
2. Q. Go에서 가장 좋아하는 기능이 뭐에요, 채널이 뭐에요?

### Redis
1. Q. LMOVE와 BLMOVE 연산 차이점
    - 우선 두 연산은 모두 source 리스트에서 데이터를 pop시켜 destination 리스트로 push하는 연산인데, source 리스트에 대해서 블록킹이 되느냐 그렇지 않느냐 차이가 있습니다. LMOVE는 블록킹 로직이 없어 source 리스트가 비어있다면 바로 null을 반환하고 끝이 나게되고 BLMOVE는 무기한 혹은 지정한 시간 동안 대기후 데이터가 들어오면 pop과 push를 수행하게 됩니다.
    - (공통점으로는)두 연산 모두 원자성이 보장되어서 여러 클라이언트가 연산을 동시에 수행할 때 리스트가 깨질 수 있는 위험성이 없고, 레디스가 싱글 쓰레드로 동작하기 때문에 race condition이 발생할 위험도 적습니다.
2. Q. KEYS와 SCAN 명령어 차이점
    - KEYS는 한번에 전체 키를 조회하는 명령어로 순간 이 명령을 처리하기 위해 레디스가 블록되어 다른 명령어가 처리될 수 없음.
    - SCAN은 반면 비동기적 탐색으로 한번에 전체 키를 반환하지 않고 점진적으로 키를 탐색하여 반환하는 명령어.
3. Q. 레디스를 어떻게 사용하셨나요?
    - 저희는 레디스를 상태 저장소로 사용했습니다. 뒷단에 별도의 RDB가 있지 않았고 레디스를 하나의 DB처럼 사용하였고 추론 API 파이프라인에 필요한 정보를 상태값으로서 레디스에 저장하고 매 추론시마다 조회하여 요청을 분배하는 등으로 사용했습니다. 모델들은 kserve 기반으로 각각 하나의 서버로 떠있다고 보시면 되고 모델 컨테이너별로 URL을 가지게 되어 API 서버가 클라이언트로부터 받은 요청을 확인하여 알맞은 모델 컨테이너를 호출하는 형태입니다.
    - 그렇게 설계한 이유는 우선 추론 트랜잭션으로 생성되는 데이터가 DB에 저장되는 구조가 아니었고, 추론 결과에 개인정보가 있을수도 있어서 그렇게 해서도 안되었습니다.
    - RDB의 캐시 용도로 사용한 것이 아니어서 캐쉬 read/write strategy를 고민하는 설계가 들어가 있지도 않았습니다.
    - 레디스에 저장되는 가장 중요한 상태 데이터는 각 모델 컨테이너들의 liveness와 url이었습니다. liveness의 경우 별도 15초 단위의 헬스체크로 주기적으로 업데이트가 되는 상태값이어서 레디스가 장애 시 재기동될 때의 마지막 상태값이 크리티컬하게 현재 실제 모델 컨테이너의 상태들과 100% sync 되어 있어야 할 필요는 없었습니다. 레디스 서버가 기동된 직후부터 바로 헬스체크가 시작되기 때문에 백업 데이터의 싱크율이 100% 확보되는 것의 중요성은 다소 떨어졌습니다.
    - 그보다 요청을 분배하기 위해 각 모델 컨테이너들의 liveness와 url을 리스트로 관리하여 circular하게 순회하며 round robin 방식으로 로드밸런싱을 수행했는데 이 때 여러 클라이언트(API 서버의 http 요청 컨텍스트)가 하나의 리스트에 접근하기 때문에 이를 트랜잭션화하는 것이 중요하였습니다.

4. Q. 그래도 캐시 전략에 대해서 설명해보세요
    - 아 네 read 전략과 write 전략이 있다고 알고있는데 RDB와 캐쉬 db를 같이 사용할 때 일반적으로 read look aside 방식과 write around 방식으로 사용하는 것 같습니다.
    - read look aside는 데이터를 찾을 때 항상 먼저 캐쉬를 뒤진 뒤 데이터를 찾으면, 즉 캐쉬 hit가 발생하면 그 데이터를 사용하고 그렇지 않으면, 캐쉬 miss가 발생하면 RDB에서 데이터를 조회하게 됩니다. 캐쉬 db가 죽더라도 RDB에서 데이터를 찾는 로직이 있어서 서비스 가용성을 확보할 수 있는 방법입니다.
    - write around는 기본적으로 모든 데이터 write는 RDB에만 하도록 하며 캐쉬 miss가 발생했을 때 RDB와 캐쉬에 모두 데이터를 write하는 방법입니다.
    - 두 방식을 조합하면 서비스 안정성을 확보할 수 있고 캐쉬 miss가 발생하게 되는 필요한 데이터가 캐쉬에 올라가게 된다는 장점이 있다고 생각됩니다. 단 서비스의 데이터 성격에 따른 적절한 ttl 값 설정이 필요합니다.

    - AOF는 모든 데이터 write가 명령어 단위로 기록이 되고 그 파일을 기반으로 재기동 시 replay되어 직전 상태로 recovery되는 방식으로 알고있는데, 저희가 레디스에 저장하는 데이터들이 레디스 종료 직전 상태와 100%  동일하게 sync되어야 하는 성격이 아니었습니다.
    - 레디스에 active하게 저장하는 데이터 중 가장 업데이트가 빈번한 것이 주로 15초 단위로 발생하는 헬스체크 결과인데, 레디스 재기동 상황에 대비하기 위해 이 데이터에 관련해서는 레디스 서버가 재기동 될 때마다 헬스체크가 한번씩 이루어지고 이후 15초 주기가 시작되어서 이 데이터는 레디스 서버 재기동 직후 최신 상태로 follow-up이 가능했습니다, `즉 데이터가 쉽게 최신 상태로 재생성이 가능했습니다.`
    - 그 외 모델 컨테이너들에 오토 스케일링이 적용되어있는 아키텍처는 아니고 더불어 라이브 업데이트가 빈번하지 않아 초기 레디스에 write된 상태 데이터가 오랜 기간 동일한 값으로 유지되는 성격이었습니다.
    - 이에 더해 uptime SLA가 99.99% 수준은 아니었기 때문에, 레디스가 죽었을 때 온콜이 알림을 받아서 장애 인지 후 RDB 방식의 백업본을 기반으로 자동으로 살아나는 정도의 downtime을 가져가면서 비용은 낮추는 방식을 택했습니다.
    - 추가로 AOF를 채택하지 않은 설계상의 이유로는, AOF는 매 write 명령어마다 fsync 시스템콜 기반의 디스크 I/O 작업을 발생시키는데 측정해본적은 없지만... 이 과정 때문에 성능저하가 크다고 알고있습니다. 또 디폴트로는 1초마다 한번씩 fsync로 레디스 프로토콜 포맷의 aof 로그를 디스크에 동기화시키기 때문에, 그 1초 동안의 데이터 손실이 있을 수 있고 이를 방지하려면 더더욱 성능 저하가 심해져서 결론적으로 저희의 비즈니스상의 장애 위험도와 데이터 성격, 성능 요건 측면에서 aof가 적절하지 않다고 판단하여 rdb 방식으로 60초마다 1개의 key 변경 시 덤프 파일을 업데이트 하는 방식으로 가기로 하였습니다.

### C
1. Q. cache coherent
    - 프로세서가 한개인 싱글 프로세서 환경에서는 캐시가 여러 레벨로 존재할 때 한 캐시에 일어난 변경을 다른 계층의 메모리에 바로 전달할 것인지 정하는 정책이 있는데 변경점을 바로바로 다른 계층 메모리로 전파하여 일관성을 해결하는 방법을 write throught, 변경이 일어난 레벨의 캐시에만 저장해두고 이후 변경이 일어난 line이 캐시에서 evicted(방출)될 때 메인 메모리에 반영하는 방법을 write back이라고 함.
    - multicore는 하나의 cpu에 core라는 독립적인 실행 유닛이 두 개 이상 존재하는 것
    - multiprocessor는 두 개 이상의 cpu가 존재하는 구조
    - 구조체가 메모리의 짝수 번지에 시작할 수 있도록 16바이트 단위로 끊는 것은 false sharing 방지
2. Q. select와 epoll의 차이에 대해서 설명해주세요
    - select와 epoll 모두 I/O 멀티플렉싱을 위한 시스템 콜인데 작동 메커니즘과 성능,  확장성에 차이가 있습니다.
    - select는 FD의 이벤트나 상태를 확인하기 위해서 모든 FD를 확인하는데 epoll은 이벤트 기반으로 상태가 변경된 FD만 확인합니다
    - 때문에 select는 사용이 간단하지만 FD 수가 많을수록 성능이 저하되고 epoll은 복잡하지만 FD 수와 무관하게 일정 성능이 유지되어 대규모 시스템에 적합합니다.
    - 또 select는 FD 개수가 1024개로 제한되는데 epoll은 관심사로 등록할 FD의 개수에 제한이 없기도 합니다.

### Linux
1. Q. cgroup이 뭐에요?
    - cgroup은 프로세스의 자원 사용을 제한하고 격리하는 커널 모듈입니다. 컨테이너 기술에서는 각 컨테이너가 서로 격리되고 할당된 크기만의 자원을 사용하여 동작하도록 제한하는 역할을 합니다. 대표적으로 cpu와 메모리의 사용량을 관리하는데 이런 각 리소스에 대한 자원 관리 범주를 컨트롤러라고 부릅니다. 서로 다른 컨테이너는 계층 구조로 각기 독립된 cgroup 그룹을 가져 컨테이너 간 자원  사용에 대해서 서로 영향을 주지 않는 것을 가능하게 해줍니다.
    - 예를 들어 1GB 메모리와 2 core CPU를 사용하도록 제한된 컨테이너는 cgroup 경로 /sys/fs/cgroup/{memory,cpu}/  하위에 컨테이너 ID 이름으로 cgroup이 매핑되어서 해당 디렉토리에 자원 제한량이 기록되고 시스템이 이를 참조하도록 합니다.
    - 쿠버네티스에서 같이 동일한 pod 내부의 컨테이너 같은 경우에만 동일한 cgroup 계층을 공유하게 되고 그렇지 않으면 대부분 독립적인 cgroup 계층을 가지게 됨.
2. Q. cgroup v1, v2  차이는 뭐에요?
    - cgroup v1은 rhel 8 버전과 ubuntu 20.04까지의 디폴트 기능이고 cgroup v2는 rhel 9버전대부터의 디폴트 기능입니다.
    - v1은 각 컨트롤러(cpu, memory)에 대해 별도의 계층 구조를 가져 사용할 때의 설정이 복잡합니다.
    - v2는 모든 컨트롤러가 단일 계층 구조로 통합되어있어 사용할 때의 설정이 간편합니다.
    - 실제로 mount 명령어로 cgroup을 확인해보면 v1은 cpu, memory, devices 등 여러줄이 나오는데 v2는 하나의 단일 계층만 확인됩니다.
3. Q. NUMA 노드 설정이란
    - 멀티프로세서 환경에서 시스템의 메모리 접근 방식을 최적화하기 위해 NUMA 아키텍처를 사용한다는 것. 각 프로세서가 가까운 메모리를 우선적으로 사용하고 멀리있는 메모리는 덜 사용하도록 하는 것
    - NUMA 아키텍처에는 로컬 메모리와 원격 메모리 개념이 있음.  로컬 메모리는 프로세서가 직접 연결된 메모리,  원격 메모리는 다른 프로세서에 연결된 메모리.
    - 각 CPU와 메모리 블록은 `노드`라는 단위로 묶이고 이 노드들이 연결되어 시스템을 구성함.  그래서 CPU 0, 1과 메모리 0을 NUMA node 0, CPU 2, 3과 메모리 1을 NUMA node 1로 매핑하는 작업을 뜻함.  추가로 affinity 설정까지도 포함될 수 있을듯.
4. Q. CPU 코어 하나는 하나의 일만 하나요?
    - 아니요 그렇지 않다고 봐야할것 같습니다. 첫번째로 인텔 CPU라고 한다면 하이퍼 쓰레딩 기술로 물리적인 코어 하나가 논리적인 두 개가 되어 각각 따로 일을 할 수 있습니다.
    - 둘째로 파이프라이닝을 활용하면 하나의 코어를 구성하는 모듈들이 각각 따로 한 명령어를 구성하는 산술 연산이나 데이터 조회 등을 수행할 수 있어 이런 관점에서도 여러 일을 동시에 처리한다고 볼 수 있습니다.
    - 마지막으로 CPU와 컴파일러 레벨에서 지원하는 SIMD 연산을 사용하면 하나의 작업으로 여러 연산을 수행할 수도 있는데 이런 경우도 있습니다.

### Container
1. Q. 왜 도커가 아니고 팟맨을 썼나요?
    - 이유는 환경적 이유 두 가지로 말할 수 있을 것 같습니다. 첫번째는 우선 서버 OS가 레드햇 엔터프라이즈였고 이는 즉 벤더로부터 테크 서포트를 지원 받을 수 있다는 것입니다. 도커의 경우 레드헷 엔터프라이즈 기술 지원에 포함되지 않고 팟맨의 경우는 레드햇 공식 지원에 포함되는 패키지이기도 하고 동시에 레드햇 엔터프라이즈에서 프로덕션 레벨에서 네이티브하게 안정적으로 운용이 가능한 레퍼런스가 많기 때문에 팟맨을 사용했습니다.
    - 둘째로는 특정 고객사의 경우 root 권한으로 애플리케이션을 띄우기 힘든 경우가 많은데, 이를 고려해서 일반 사용자 계정으로 루트리스 모드로 컨테이너를 띄워야 했는데 이 경우 도커보다 팟맨이 태초 사상부터 루트리스를 고려하고 만들어졌기 때문에 운용이 용이했고 컨테이너 스토리지 마운트나 네트워크 사용 등과 같은 기능을  root  일 때와  동일한 수준으로 사용할 수 있어서 팟맨을 사용하였습니다.
